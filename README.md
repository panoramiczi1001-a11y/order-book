# Order Book（限价订单簿）

从零写一个限价订单簿：下单、撤单、撮合、成交回报、行情快照。

这不是一个从零开始的项目——`v0/` 是我 2026 年 9 月参加一家量化私募的笔试题答卷。
当时的评语是「这里都是问题」。这份仓库就是我逐条把它们改掉的过程。

**为什么要公开这段不体面的起点**：一个订单簿的骨架谁都能写出来，
难的是知道它错在哪、以及为什么这么改。所以 `v0/` 一个字不改地留着。

## 目录

```
v0/                笔试原始答卷，只读存档，不改
src/
  order.h/.cpp       订单、价格（整数 tick）、成交记录
  order_book.h/.cpp  单标的簿子：下单 / 撤单 / 撮合 / 盘口
  exchange.h/.cpp    按标的路由的多本簿子
  main.cpp           演示程序
CMakeLists.txt     构建脚本（核心库 + 演示程序 + 测试）
tests/
  test_parity.cpp    随机对拍：冻结撮合行为
  test_v3.cpp        v3 新增行为的定点测试
```

## 构建

```
cmake -B build
cmake --build build
./build/order_book
```

Windows 上可以直接用 Visual Studio 打开这个目录（VS 2019+ 原生支持 CMake）。

跑测试：

```
ctest --test-dir build --output-on-failure
```

## 测试为什么这么写

`test_parity.cpp` 是随机对拍：一边跑本仓库的实现，一边跑一份故意写得很笨的参考实现
（`vector` 存全部订单，每次撮合重新扫一遍找最优价），每一步比对盘口是否一致。

它不判断「什么是对的」，它做的是**把行为冻住**——重构之后输出必须一字不差，
否则说明行为被无意改动了。v3 换掉了底层数据结构，正是靠它证明「撮合结果没变」。

`test_v3.cpp` 补的是新增语义的定点断言：多标的隔离、订单号终身不复用、
非法输入被拒、成交记录内容、撤单后序列号仍不可复用、同价位时间优先。

## 基准（v3 基线）

口径：单次操作逐个计时取分位数，另用批处理测吞吐。**两者不可混用**——单次计时会掺入
计时器开销（本机约 20 ns），所以吞吐用批处理，分位数只用于看尾部形状。

```bash
cmake -B build && cmake --build build
./build/order_book_bench insert 200000
./build/order_book_bench cancel 200000
./build/order_book_bench mixed  200000
./build/order_book_bench throughput 500000
```

x86-64 / Intel Core Ultra X9 388H（Linux VM, 2 vCPU）/ g++ -O2 / 单位 ns：

| 场景 | p50 | p90 | p99 | p999 | mean |
|---|---|---|---|---|---|
| insert（20 万笔） | 85 | 103 | 1101 | 1910 | 166 |
| cancel（撤 10 万笔） | 230 | 389 | 534 | 814 | 312 |
| cross+match | 860 | 2751 | 6231 | 46866 | 1856 |
| 吞吐（批处理） | — | — | — | — | 188.5 ns/op（5.31 M ops/s） |

三个值得记住的现象：

1. **均值远高于 p50**（insert 166 vs 85）。尾部把均值拉走了，所以只报平均值的基准会误导人。
2. **撤单比下单慢**（230 vs 85）。撤单要查哈希、摘链表节点、可能还要删整个价位、同时写入 `retired_`。
3. **撮合贵一个量级**（860 ns）。它是「插单 + 撮合循环」的合计，且每轮撮合可能产生多笔成交。

后续每次改数据结构，都拿这张表对比，重点看 **p99 与 p999**，而不是均值。
